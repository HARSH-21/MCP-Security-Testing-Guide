# 3.10 Input Validation (`INPV`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

Input validation tests focus on **tool arguments**: type confusion, boundary checks, path traversal, and JSON/schema mismatches between what the host sends and what the server enforces.

## Why this category matters

Tools often wrap shell commands, file APIs, or SQL. Model-generated arguments are attacker-controlled input even when the user appears benign.

## Scope

Parameter validation, canonicalization, path joins, schema enforcement vs runtime behavior, nested JSON edge cases.

## When to prioritize

Critical for tools wrapping filesystem, shell, or query interfaces.

## Related categories

[TOOL](3.05-tool-security.md), [OUTV](3.11-output-handling.md)

## Common test chains

INPV-02 + RSRC-05; INPV-03 + TOOL-04 (schema manipulation).

## Threats and attack patterns

Input bugs below are defects in how a server or client handles a value the caller, or a remote MCP server, supplied. They are quoted from advisories. Crossing a filesystem root is also an authorization failure; see [3.4](3.04-authorization-permission.md) and [3.6](3.06-resource-data-access.md).

### Path parameters that ignore the configured directory

[CVE-2026-40576](https://github.com/advisories/GHSA-j98m-w3xp-9f56) says `excel-mcp-server` through 0.1.7 takes a `filepath` argument on its tool handlers and passes it to `get_excel_path()`. The advisory says that function does not enforce `EXCEL_FILES_PATH`: absolute paths are returned as given, and relative paths are joined without a resolve-and-check. The advisory’s precondition for remote use is the SSE or Streamable HTTP transport, default bind `0.0.0.0`, and no authentication. Fixed versions are those after 0.1.7; confirm the patched release in the advisory before you cite a fix version in a report.

[CVE-2026-27825](https://github.com/advisories/GHSA-xjgw-4wvw-rgm4), `mcp-atlassian` before 0.17.0, is the write path. `download_path` on `confluence_download_attachment` is used as the output file. The advisory says `os.path.abspath()` does not constrain the directory, and `target_dir` on `download_content_attachments` is the same class of parameter. Fixed in 0.17.0.

**Tests:** `MCPSTG-INPV-02`. Include both an absolute path and a relative path that leaves the root after resolution. Record the process user’s rights, because the advisory’s impact is “any path the server process can write,” not “any path on the machine.”

### Command and query strings reached an interpreter

[CVE-2025-6514](https://www.cve.org/CVERecord?id=CVE-2025-6514) is CWE-78 in an MCP client. `mcp-remote` 0.0.5 through 0.1.15 takes `authorization_endpoint` from the MCP server’s OAuth metadata and, per the CVE text, is exposed to OS command injection from that URL. CVSS 3.1 9.6. Fixed in 0.1.16 ([GHSA-6xpm-ggf7-wc3p](https://github.com/advisories/ghsa-6xpm-ggf7-wc3p); [JFrog](https://jfrog.com/blog/2025-6514-critical-mcp-remote-rce-vulnerability/)). The MCP security document’s rule that matches this bug: clients must not open authorization URLs by invoking a shell ([Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices), 28 July 2026 docs).

[CVE-2026-59971](https://osv.dev/vulnerability/CVE-2026-59971) is the SQL form. Before MySQL MCP Server 0.4.2, a query supplied to `execute_sql` reaches `cursor.execute` on an SSE transport that the CVE says does not authenticate. That is missing authentication and missing query restriction together. The CVE does not describe a separate sanitizer bypass on the stdio transport.

Checkmarx’s 1 October 2025 report on `@lanyer640/mcp-runcommand-server` says version 1.0.5 executed received commands with `shell: true` and without authentication, and version 1.0.6 added a reverse shell ([Checkmarx Zero](https://checkmarx.com/zero-post/npm-malware-alert-lanyer640-mcp-runcommand-server-with-reverse-shell/)). The package was removed from the public npm registry. Treat any remaining cached copy as malicious, not as a validation bug to patch in place.

**Tests:** `MCPSTG-INPV-01`, `MCPSTG-TOOL-03`.

### Schema and extra fields

This guide did not find a CVE whose sole published defect was “an extra JSON field confused an MCP tool schema.” Two published patterns still belong in `MCPSTG-INPV-03`:

- Tool descriptions and parameter schemas are model-visible instructions. Invariant (1 April 2025) showed a parameter (`sidenote` in their demonstration tool) whose description told the model what to put in it, while the user interface did not show the full value. The schema was doing double duty as an injection point. See [3.5](3.05-tool-security.md). Do not copy that demonstration schema into a report; record whether your client displays every property the model is given.
- [CVE-2026-27826](https://github.com/advisories/GHSA-7r34-79r5-rcc9) is header-level schema confusion: `mcp-atlassian` treated `X-Atlassian-Jira-Url` and `X-Atlassian-Confluence-Url` as the base URL of the upstream product and did not validate the destination. The advisory says the first fetcher call then requested `{header url}/rest/api/2/myself`. The input is not a tool argument. It is still caller-controlled structured input that selected a network target. A later project advisory, [GHSA-72fm-whvq-jghf](https://github.com/sooperset/mcp-atlassian/security/advisories/GHSA-72fm-whvq-jghf), says the 0.17.0 check resolves the name at validation time and the HTTP client resolves it again when it connects, so the two lookups can differ.

OWASP API Security discusses mass assignment as a general API issue. Do not label a finding “mass assignment” unless the server actually binds client JSON onto an internal object. For MCP, the evidence to collect is: which fields the schema declares, which fields the handler reads, and which of those fields can change a path, a URL, a command, or a recipient.

**Tests:** `MCPSTG-INPV-03`.

### Canonical attack patterns

Input-validation patterns in this section name the abuse, a lab-safe example, the impact, red flags, and defensive checks. Published cases earlier in this section remain the sourced record.

### Dangerous Command Execution

The canonical write-up is [Dangerous Command Execution](3.05-tool-security.md#dangerous-command-execution) in section 3.5. Use it for shell, script, and arbitrary-execution tools. In this section, test the argument path with `MCPSTG-INPV-01` and path handling with `MCPSTG-INPV-02`.

### Execution safety

* Avoid generic shell tools.
* Prefer narrow, purpose-built tools.
* Validate all tool arguments server-side.
* Sandbox local servers and command execution.
* Restrict network access for local tools, and check URL destinations at connect time.
* Validate `Origin` and `Host` on any HTTP listener, including localhost.
* Open authorization URLs with a URL API, never a shell. Allow only `http` and `https`.
* Apply timeouts and resource limits.

# MCPSTG-INPV-04 — Test Input Validation and Continuation-State Integrity in Multi-Round Requests

<a id="mcpstg-inpv-04"></a>

#### Summary

This test evaluates whether an MCP server securely validates input and protects continuation state throughout Multi-Round Trip Requests (MRTR), introduced in the MCP 2026-07-28 specification.

MRTR allows an MCP server to request additional input while processing an original client request. Instead of initiating a separate server-to-client request over an open connection, the server returns an `InputRequiredResult` containing `resultType: "input_required"` and `inputRequests`. The client fulfils those requests and retries the original method with `inputResponses` and the echoed `requestState`.

Because the client returns data supplied by the server in a subsequent request, the server must not automatically trust the received continuation data.

Insufficient validation or protection of continuation state may allow an attacker to manipulate inputs, reuse state across requests or identities, bypass application-level validation, or influence unintended downstream operations.

This test focuses on:
- Validation of client-provided `inputResponses`.
- Integrity and trustworthiness of `requestState`.
- Binding continuation state to the originating request and authenticated principal where applicable.
- Prevention of unauthorized state reuse and unintended execution during subsequent rounds.

Perform this test only against implementations supporting MRTR under the applicable MCP protocol revision.

#### Scenario

- **MCP host/client:** `<TEST_CLIENT>` using `<TEST_ACCOUNT>`.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` exposing `<TARGET_TOOL_OR_WORKFLOW>`.
- **MCP protocol version:** `2026-07-28`.
- **Target method:** `tools/call`, `prompts/get`, or `resources/read`, as applicable.
- **Workflow:** A multi-round interaction requiring additional client input.
- **Trust boundary:** MCP client/host ↔ MCP server ↔ downstream application or service.
- **Attacker position:** An authenticated or unauthenticated client, as defined by the test scope, capable of modifying or replaying client-supplied continuation data.
- **Potential impact:** Input validation bypass, unauthorized operations, continuation-state manipulation, cross-user data access, or unintended downstream execution.

#### Test Objectives

- Identify MCP methods and workflows that support MRTR.
- Verify that the server validates every client-provided `inputResponses` value according to the corresponding request type and application-level requirements.
- Verify that `requestState` is treated as untrusted client-provided data when received again.
- Check whether continuation state is protected against unauthorized modification.
- Verify that continuation state is associated with the originating request and authenticated principal where relevant.
- Test whether expired, invalid, or improperly reused continuation state can affect application behaviour.
- Confirm that invalid continuation data cannot trigger unauthorized downstream operations or leave inconsistent application state.

#### Preconditions

- Written authorization and an isolated lab environment.
- An MCP server implementing the 2026-07-28 MRTR mechanism.
- A documented target method that can return an `InputRequiredResult`.
- A valid baseline request that successfully completes the multi-round workflow.
- At least one workflow that uses `inputRequests` and accepts corresponding `inputResponses`.
- Access to relevant server-side logs and downstream operation records, where available.
- Two test accounts or principals if cross-principal state reuse is being evaluated.
- Synthetic data and non-production resources.
- A safe mechanism to inspect and modify test requests and responses.

#### How to Test

##### 1. Manual Review

Review the MCP server implementation and workflow documentation to identify:

- Methods that can return `InputRequiredResult`.
- How `inputRequests` are generated and how their response types are defined.
- How `inputResponses` are processed and validated.
- How `requestState` is generated, stored, verified, and consumed.
- Whether continuation state contains information affecting authorization, resource access, or business logic.
- Whether the server binds continuation state to the originating method, request parameters, and authenticated principal where applicable.
- Whether the server implements expiration, replay protection, and request-size or round limits.

Identify which validation controls are enforced by the server rather than relying exclusively on client-side validation.

##### 2. Configuration Review

Inspect:

- Tool, prompt, and resource input schemas.
- Server-side validation logic for each supported input request type.
- Validation of elicitation responses and their requested schemas.
- Integrity protection mechanisms for `requestState`, such as HMAC or authenticated encryption (AEAD), where state influences security-sensitive decisions.
- Expiration and request-binding mechanisms for continuation state.
- Principal and authorization-context verification.
- Maximum input size, continuation rounds, and processing limits.
- Error handling and logging for invalid continuation requests.

Do not expose secrets, signing keys, or production values during evidence collection.

##### 3. Runtime Testing

1. Initiate a valid request against a supported MCP method and capture the original JSON-RPC request.

2. Verify that the server returns an `InputRequiredResult` with `resultType: "input_required"` and the expected `inputRequests`.

3. Capture the returned `requestState`, if provided, and record the original request parameters and authenticated identity.

4. Complete the requested input using a legitimate client response. Verify that the client retries the original method with the corresponding `inputResponses` and echoes `requestState` unchanged.

5. Confirm that the server successfully validates the response and completes the operation as expected.

6. Repeat the workflow with modified `inputResponses`, including:
   - Incorrect response types.
   - Missing required response content.
   - Invalid or out-of-schema values.
   - Malformed response structures.
   - Unexpected values that violate application-level constraints.

7. Where applicable, test boundary conditions such as oversized input, excessive array elements, invalid numeric ranges, and excessive nesting.

8. Modify the returned `requestState` before submitting the retry. Verify that invalid or tampered state is rejected whenever its integrity is required for security-sensitive processing.

9. Attempt to reuse continuation state with a different original method, tool, request parameters, or resource reference. Verify that the server does not accept state outside its intended request context.

10. Where authenticated identities are supported, initiate a workflow using one test account and attempt to continue it using another account. Verify that continuation state cannot be used to access another principal's workflow or privileges.

11. Where the implementation enforces state expiration or single-use semantics, attempt to reuse expired or previously consumed continuation state.

12. Verify that invalid continuation data does not execute the downstream operation, create unintended persistent objects, or leave the workflow in an inconsistent state.

13. Repeat the tests with a fresh workflow to ensure that observations are not caused by residual state from previous requests.

##### 4. Abuse Case Testing

Using synthetic lab data only:

- Submit valid initial input followed by malformed or out-of-policy `inputResponses`.
- Modify client-returned `requestState` and check whether integrity verification detects the modification.
- Attempt to reuse valid continuation state with a different tool or request.
- Attempt continuation-state reuse across different authenticated principals.
- Replay previously used or expired continuation state where the implementation defines corresponding expiry or single-use controls.
- Supply unexpected response content and verify that it does not influence application behaviour outside the requested input contract.
- Attempt repeated invalid continuation requests to identify inadequate processing limits or resource consumption.
- Test whether a valid continuation can be manipulated to change the target resource, tenant, or effective authorization context.

Do not assume that accepting an unrecognized optional field is itself a vulnerability. Assess whether it changes processing, bypasses validation, or violates the applicable protocol or application requirements.

Avoid destructive payloads and stop testing if shared services or unintended resources are affected.

##### 5. Log and Detection Review

Verify that server logs can correlate the original request and subsequent rounds without exposing sensitive information.

Check whether logs record:

- The original MCP method and affected tool or resource.
- The continuation round and relevant request correlation identifier.
- Whether `inputResponses` passed or failed validation.
- Whether `requestState` verification succeeded or failed, where implemented.
- Whether the authenticated principal matched the expected identity.
- Whether a downstream operation was attempted or executed.
- Whether the workflow was safely terminated after invalid continuation data.

Logs should not expose secrets, authentication tokens, signing keys, or unnecessary user-provided sensitive content.

#### Expected Results

**Secure Result:**

- The server validates `inputResponses` according to the corresponding request type and applicable application-level constraints.
- Invalid or malformed response content is handled safely.
- The server treats received `requestState` as untrusted input.
- State integrity is protected whenever continuation state influences authorization, resource access, or business logic.
- Invalid or tampered state is rejected before security-sensitive processing.
- Continuation state is appropriately bound to the originating request and authenticated principal where relevant.
- Expired or reused state is handled according to the implementation's security policy.
- Invalid continuation requests do not trigger unauthorized downstream operations or unintended persistent changes.
- Errors do not disclose secrets, internal state, or sensitive implementation details.

**Potential Finding Indicators:**

- Malformed `inputResponses` are accepted and influence sensitive downstream operations.
- The server trusts client-returned `requestState` without verifying its integrity when it influences security-sensitive decisions.
- Modified continuation state allows an attacker to change the intended operation or resource.
- Continuation state can be reused across unrelated requests or authenticated principals, resulting in unauthorized access.
- Expired or consumed continuation state can bypass implemented security controls.
- Invalid continuation input causes partial execution or persistent inconsistent state.
- Repeated invalid continuation requests cause resource exhaustion due to inadequate limits.

A protocol or validation difference alone is not sufficient to establish a security vulnerability. Document the actual security impact and applicable control violation.

#### Remediation

- Apply server-side validation to all client-provided `inputResponses` according to their corresponding request types and application-level schemas.
- Treat all client-returned continuation data as untrusted.
- Protect security-sensitive `requestState` using integrity mechanisms such as HMAC or authenticated encryption (AEAD).
- Bind continuation state to the originating request, relevant parameters, and authenticated principal where applicable.
- Implement appropriate expiration and replay protections for continuation state.
- Reauthorize sensitive operations when the effective identity, target resource, or authorization context may change.
- Reject invalid or improperly verified continuation state before performing sensitive operations.
- Ensure validation is applied to the final values used by downstream components.
- Apply appropriate limits to input sizes, continuation rounds, processing time, and resource consumption.
- Avoid partial side effects when continuation validation fails.
- Maintain security-relevant audit logs while minimizing sensitive information.

#### Evidence to Collect

- Sanitized original MCP request and `InputRequiredResult` response.
- Sanitized continuation request containing `inputResponses` and `requestState`.
- Valid and invalid input test results.
- Evidence of continuation-state modification and verification outcomes.
- Cross-principal or cross-request reuse test results, where applicable.
- Relevant input schemas and server-side validation configuration.
- Correlated logs showing whether downstream operations were executed.
- Reproduction steps and demonstrated security impact.
- Remediation and retest results, where available.
